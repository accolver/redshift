# release-integrity Specification

## Purpose
Define authenticated, reproducible, atomic, platform-accurate installation, upgrade, build, and release requirements.
## Requirements
### Requirement: Authenticated Release Artifacts
Production releases SHALL include exact-name SHA-256 metadata, SPDX SBOM, provenance, and artifact attestations bound to the expected repository, workflow, immutable tag, commit, artifact name, and digest. Every advertised platform artifact SHALL exist before the release is considered complete.

#### Scenario: Complete trusted release
- **WHEN** a release artifact and all trusted metadata verify
- **THEN** it is eligible for installation or upgrade

#### Scenario: Missing or invalid trust material
- **WHEN** an attestation, exact manifest entry, digest, or expected identity is missing, malformed, duplicate, or invalid
- **THEN** installation/upgrade fails closed

#### Scenario: Public release certification
- **WHEN** a release workflow reports success
- **THEN** an independent verifier can download each supported artifact, verify its checksum and GitHub attestation against `accolver/redshift`, and execute its version/help smoke contract

#### Scenario: Partial release
- **WHEN** any supported binary, checksum, SBOM, attestation, or verification job is absent or failed
- **THEN** the release is not certified as production-ready and shall not remain the latest advertised release

### Requirement: Atomic Install and Upgrade
Install/upgrade SHALL download to a restrictive same-filesystem temporary path, verify before executable permission, smoke-test the candidate, atomically replace the target, and preserve/restore the previous binary on failure or interruption.

#### Scenario: Hash mismatch
- **WHEN** a candidate hash does not match trusted metadata
- **THEN** the existing binary remains unchanged and no executable partial remains

#### Scenario: Smoke-test failure
- **WHEN** a verified candidate fails `--version`
- **THEN** the previous binary is restored

### Requirement: Immutable Build and Deployment Inputs
CI/release SHALL pin action commits and Bun/tool versions, use frozen dependency installs, default to read-only permissions, and grant write/OIDC/attestation permissions only to the job requiring them. Relay deployment SHALL receive a least-privilege token through environment or hidden input and use repository-pinned tooling.

#### Scenario: Policy check
- **WHEN** a workflow uses a mutable action tag, latest toolchain, unfrozen install, or workflow-wide write permission
- **THEN** the release policy gate fails

#### Scenario: Relay deploy token
- **WHEN** deployment starts without a secure token source
- **THEN** it fails before network mutation and never accepts a token in argv

### Requirement: Supported Platforms Match Artifacts
The updater SHALL advertise and select only platforms for which the release produces verified artifacts.

#### Scenario: Unsupported Windows upgrade
- **WHEN** a Windows client requests upgrade without Windows artifacts
- **THEN** it exits with an explicit unsupported-platform error before download

### Requirement: Generated Artifact Consistency
Release gates SHALL verify that committed embeds record the current deterministic source digest, rebuild embedded dashboard and relay worker artifacts from source, and require same-run regeneration to be byte-identical. Platform-specific bundler chunking SHALL not make a Linux release depend on macOS-generated bytes.

#### Scenario: Stale generated artifact
- **WHEN** embedded source inputs change without regeneration, or repeated generation on one runner differs
- **THEN** CI/release fails before compiling release artifacts

### Requirement: Documented Release Ceremony
`AGENTS.md` SHALL document the exact preflight, Release Please, workflow monitoring, artifact verification, clean-install, rollback, and incident commands used for a full GitHub release.

#### Scenario: Agent performs a release
- **WHEN** an agent is instructed to publish a production release
- **THEN** it follows the documented ceremony, stops on any failed gate, and records tag, commit, workflow, assets, and verification evidence

### Requirement: Immutable Release Recovery
Published release assets SHALL never be silently replaced to repair a defect. A failed or bad release SHALL be withdrawn from latest status and corrected by a new patch release.

#### Scenario: Defective published artifact
- **WHEN** post-publication verification detects a bad artifact or claim
- **THEN** maintainers preserve evidence, remove latest/recommended status, publish an incident note, and issue a new version rather than using `--clobber` to mutate trusted bytes
